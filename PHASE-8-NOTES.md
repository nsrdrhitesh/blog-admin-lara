# Phase 8 — REST API

## Inventory check first
Given what happened in Phases 6 and 7, I checked the project state before
writing anything this time. `app/Http/Controllers/Api/` and
`app/Http/Resources/` existed but were genuinely empty (just the Phase 1
scaffold folders), and `routes/api.php` was still the Phase 1 placeholder
health-check stub. Nothing to reconcile this time — clean build.

## What's included
Every endpoint from the spec's API list, each backed by a Laravel API
Resource (never a raw model dump):

- `GET /api/blogs` — filters: `category`, `tag`, `author` (all by slug),
  `search`, `per_page` (capped at 50)
- `GET /api/blogs/{slug}` — full detail, and **records a view** on every
  hit (`BlogService::recordView()` — a `blog_views` row plus incrementing
  the denormalized `view_count` used for trending)
- `GET /api/categories` — active only, top-level with one level of children nested
- `GET /api/tags`, `GET /api/authors` — active only
- `GET /api/search?q=` — title/description/content search
- `GET /api/latest`, `GET /api/trending`, `GET /api/featured` — `limit` param, capped at 30
- `GET /api/related/{slug}` — reuses `BlogRepository::related()`, which
  already existed from Phase 3

**Two Blog resources, on purpose**: `BlogResource` (list endpoints — id,
title, excerpt, featured image, category/author/tags, counts) vs
`BlogDetailResource` (single-post endpoint only — adds full content, every
attached image, the complete SEO block, the JSON-LD schema generated by
Phase 6's `SchemaGeneratorService` keyed by type, FAQs, and the GEO
AI-summary fields). A list of 15 posts doesn't need to carry each one's
full JSON-LD payload.

## A caching bug caught and fixed before it shipped
First pass cached `latest`/`trending`/`featured` under a key that included
the requested `?limit=`, e.g. `api:latest:10`, `api:latest:25`. That's an
unbounded number of possible cache keys — there's no clean way to
invalidate "every `api:latest:*` key" without cache tags, which the
`database` cache driver (this project's default, Phase 2) doesn't support.
Fixed by caching one fixed-size result (30 items) under a single key and
slicing to the requested `limit` in PHP after reading from cache.

## Cache invalidation — extended to fix a Phase 6 gap too
While wiring invalidation for the new `api:latest`/`api:trending`/
`api:featured` cache keys, I noticed **Phase 6's sitemap and RSS caches had
the same gap** — cached with a TTL but no listener ever cleared them early,
so `BlogPublished` was dispatched into the void. Added one listener
(`ClearContentCaches`) that clears all six keys together, registered
against the existing `BlogPublished` event. It only fires on the
draft→published transition (not on every edit) — an already-published
post being tweaked doesn't change these listings' membership, only its own
content, and each cache still expires within 5–15 minutes regardless.
Category/Tag/Author list caches aren't wired to any invalidation listener
yet — same accepted trade-off, just not yet extended there.

## Design decisions worth knowing about
- `Category`, `Tag`, and `Author` gained a simple `scopeActive()` — used
  only by the public API (admin listings intentionally show inactive
  records too, for management).
- Category/Tag/Author API listings skip the Repository/Service layer and
  query the Eloquent models directly — same precedent as
  `RedirectService`/`CommentService` from Phases 6–7: no meaningful query
  complexity here to justify the interface layer. `Blog`'s API queries
  *do* go through `BlogRepositoryInterface`, extended with
  `publishedPaginate()`/`findPublishedBySlug()`/`latest()`/`trending()`/
  `featured()`/`search()` — Blog's queries are complex enough (multiple
  slug-based filters, eager loading) to earn it.
- View recording is deliberately simple — no bot filtering, no per-IP
  dedupe window. The spec asks for a working view counter, not an
  analytics pipeline; building real dedupe/bot-detection would be
  meaningfully more code for a feature not asked for.

## What's NOT yet wired up
- No API authentication/tokens — every endpoint here is intentionally
  public-read, matching the spec's list exactly. If write endpoints or
  private data are needed later, that's Sanctum, not an extension of this.
- No rate-limit tier beyond Laravel's default 60/min on the `api` group.
- Category/Tag/Author caches don't have an invalidation listener (see above).

## To try it
```bash
php artisan serve
curl http://localhost:8000/api/blogs
curl http://localhost:8000/api/blogs/your-post-slug
curl "http://localhost:8000/api/search?q=laravel"
```
